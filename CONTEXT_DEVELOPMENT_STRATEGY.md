# Mediqom Context Development Strategy

## Current State (Phases 1–4 Complete)

The context system is built on a **term-based, three-stage search pipeline**. Embeddings and vector search were fully implemented but discarded — they produced no reliable results across languages and added unnecessary infrastructure. The current implementation uses:

- **Medical terms extraction** — AI assigns standardized terms to each document during import
- **Three-stage search** — Stage 1: category filter → Stage 2: term matching with relevance scoring → Stage 3: temporal filtering ("latest", "recent", "historical")
- **MCP tools** — five production tools: `searchDocuments`, `getDocumentById`, `getAssembledContext`, `getProfileData`, `queryMedicalHistory`
- **HIPAA audit system** — all medical data access is logged

Context is assembled **on demand** for every chat. There is no persistence, no cross-session learning, and no synthesis across documents. The `profileContextManager.addDocumentToContext()` function is a no-op — it only logs.

---

## Phase 5: Document Index Page

### The Problem

Every chat session re-derives context from scratch. The AI has no memory of what documents exist, no awareness of the patient's current medications or recent lab trends, and no way to match a Czech query for "cukrovka" against a German document about "Diabetes mellitus". Context assembly is expensive and shallow.

### The Approach: Second Brain Index Pattern

Inspired by the LLM Wiki / Second Brain pattern: documents are the **source pages** (already exist, encrypted). The HealthProfile document holds **full history**. What we build is the **index page** — a lightweight per-profile catalog synthesized from all documents that gives the AI immediate orientation without re-reading everything.

One encrypted `DocumentType.internal` record per user per profile, category `'document-index'`. Three sections:

---

## Index Sections

### Section 1: `catalog` — Document Registry

Per-document entries, grouped by category. Generated by a fast LLM call on each document save.

```typescript
interface IndexEntry {
  docId: string;
  title: string;
  date: string;           // ISO date from metadata
  category: string;       // 'laboratory', 'prescription', 'radiology', etc.
  summary: string;        // 1–2 sentence narrative
  keyFacts: string[];     // ["HbA1c 7.2", "Metformin 500mg prescribed"]
}
```

Injected into system prompt grouped by category:

```
[Lab Results] 4 documents
  - Metabolic Panel (2026-03-15): HbA1c 7.2, Glucose 126 mg/dL. Worsening glycemic control.
  - CBC (2026-03-15): Normal. Mild anemia (Hb 11.2).
[Prescriptions] 2 documents
  - Metformin 500mg (2026-03-18): Started for prediabetes management.
```

Token estimate: ~600–900 tokens for 20 documents.

---

### Section 2: `currentState` — Active Snapshot

Synthesized from all documents. Current/active items only — **no history**. Full history lives in the HealthProfile document.

```typescript
interface CurrentState {
  medications: {
    name: string;
    dose: string;
    frequency: string;
    startDate: string;
    status: 'active' | 'stopped';
    sourceDocId: string;
  }[];
  labValues: {
    analyte: string;          // "HbA1c", "LDL", "Creatinine"
    value: string;            // "7.2"
    unit: string;             // "%"
    date: string;             // date of most recent result
    trend: 'improving' | 'stable' | 'worsening' | 'new';
    previousValue?: string;   // for trend comparison
    sourceDocId: string;
  }[];
  updatedAt: string;
}
```

Injected into system prompt as a compact block (~200–400 tokens):

```
Current Medications: Metformin 500mg 2x/day (since Mar 2026), Lisinopril 10mg/day (since Jan 2025)
Recent Labs: HbA1c 7.2% ↑ (was 6.8, Mar 2026) | LDL 124 mg/dL → | Creatinine 0.9 mg/dL ↓
```

`currentState` is updated incrementally: a new prescription document patches `medications`; a new lab document patches `labValues` with trend calculation vs. the previous value for the same analyte.

---

### Section 3: `conceptIndex` — Multilingual Alias Table

Canonical medical concepts with multilingual aliases. Used for Stage 0 search pre-filtering — **not injected into the system prompt**.

```typescript
interface ConceptEntry {
  canonical: string;         // "Diabetes mellitus type 2"
  type: 'condition' | 'medication' | 'allergy' | 'analyte' | 'procedure';
  aliases: {
    term: string;
    lang: string;
    aliasType: 'medical' | 'patient' | 'abbreviation';
  }[];
  documentIds: string[];
}
```

This solves multilingual search: a Czech query matches the alias table and finds German documents that share the same canonical concept — without any vector operations.

---

## Ownership and Encryption

The index is **per user, not per profile**. Encrypted with the **user's own RSA public key** — never with the profile key.

- User A and User B each build their own index for a shared profile
- Each index is a derived artifact from documents the user can already access
- When User B is granted access to a shared profile, their index is built on first initialization

---

## Build Lifecycle

### On document save (fire-and-forget)

After `addDocument()` completes, replace the no-op in `addDocumentToContext()`:

1. Load current index from in-memory cache
2. Fast LLM call (Haiku/Flash): pass document content + existing `currentState`
   - Returns: `IndexEntry` + `ConceptEntry[]` + `CurrentStatePatch`
3. Upsert the `IndexEntry` for this document (by `docId`)
4. Merge `CurrentStatePatch` into `currentState` (upsert lab values by analyte; append new meds)
5. Merge new `ConceptEntry` aliases into `conceptIndex`
6. Save updated index (encrypted, `DocumentType.internal`, `metadata.category = 'document-index'`)

### On profile initialization

`initializeProfileContext()` will:

1. Load the encrypted index from `DocumentType.internal` filtered by `metadata.category = 'document-index'`
2. Detect stale entries by comparing the current document list against `catalog`:
   - Document present in list but missing from `catalog` → **new** (needs IndexEntry)
   - Document present in both but `updated_at` differs → **modified** (IndexEntry must be regenerated)
   - Document present in `catalog` but missing from list → **deleted** (IndexEntry must be removed; `currentState` is dirty)
3. If any documents were **deleted**: remove their `IndexEntry` entries and mark `currentState` as dirty — rebuild `currentState` from scratch using the remaining documents (it cannot be patched; any analyte value or medication might have come from the deleted doc)
4. If ≤5 new/modified → process them individually; skip cold-start
5. If >5 new/modified, or no index exists, or `currentState` is dirty and remaining docs > 10 → cold-start rebuild in batches of 10 documents
6. Cache the index in memory for the session

### Cross-user freshness (shared profiles)

When User A imports a document to a shared profile, User A's index is updated immediately via the fire-and-forget hook. User B's index is **not** updated in real time — it is refreshed the next time User B calls `initializeProfileContext()` (i.e., next time User B opens the app and loads the profile). The staleness check at init catches the gap automatically.

This is by design: cross-user index freshness is **session-start granularity**, not real-time. No push mechanism is needed.

## System Prompt Injection

In `ai-service.ts` `buildEnhancedSystemPrompt()`, inject both sections in order:

1. `currentState` block first (~200–400 tokens) — always relevant regardless of query topic
2. `catalog` grouped by category (~600–900 tokens, capped at 1000 tokens if profile is large)

Total injection budget: ~1000–1400 tokens. When index is unavailable (cold start, first session): fall back to the current assembled-context approach.

---

## Search Integration (Stage 0)

Before Stage 1 (category filter) in `search-documents.ts`, a new Stage 0 runs:

1. Match query terms against `conceptIndex[].aliases`
2. Collect `documentIds` from all matching concepts
3. Pre-filter candidates to those IDs
4. Pass reduced set into the existing Stage 1–3 pipeline

If the index is unavailable, Stage 0 is skipped and Stage 1–3 runs on the full document set.

---

## Relationship to HealthProfile Document

- **HealthProfile** = authoritative full history: all conditions, all med history, all lab values over time
- **Index `currentState`** = current/active snapshot only: active meds, most recent lab value per analyte
- The index does not replicate HealthProfile history. The system prompt references the HealthProfile via its document ID so the AI can request it via `getDocumentById` when full history is needed.
